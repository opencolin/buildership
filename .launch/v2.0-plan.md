# v2.0 — structural (week 1-2 post-event)

> **Worktree:** `.worktrees/v2.0-structural` (branch `v2.0-structural` off `main` at `6a729b9`)
> **Window:** Week 1-2 after the June 14 boat day
> **Trigger:** Post-event retro. Build the platform we wished we had.

## Confirmed items from PUNCHLIST.md council synthesis

1. **Dynamic per-event OG system** — *(Product, Marketing, Designer)*
   - Move from static `opengraph-image.tsx` to per-route OG generators
   - `/events/[slug]/opengraph-image.tsx` returns ImageResponse with the event's
     title/date/host pulled from `data.ts` or DB
   - Every share renders bespoke, on-brand creative as the program scales
   - Foundation for hosting many events on ship.builders

2. **Idempotent migration-based data pipeline** — *(Engineering)*
   - Never let data mutation ride the build step (already partially done in v0.1
     by decoupling `build` from migrate+seed)
   - Move seed data into migration files OR into runtime fixtures
   - Schema changes go through migrations, not seeds
   - Add a `release` GH Action that runs migrations against Production before deploy

3. **Brand-asset pipeline** — *(Designer)*
   - Normalize all sponsor/host logos to one directory (`public/brand/`)
   - One canonical format per logo (SVG preferred; PNG fallbacks where needed)
   - Light + dark variants for every wordmark
   - Kill the `/public` vs `/public/brand` split that caused the duplicate
     `nebius-wordmark.svg` bug
   - Document in `public/brand/README.md` how to add a new sponsor's assets

4. **Design-token pass** — *(Designer)*
   - Codify spacing/type/color into Tailwind theme tokens
   - Goal: polish survives the next 10 content edits without drift
   - Audit existing colors: `navy-*`, `lime-*`, `ink-*`, `accent-*` (data.ts uses
     `accent-sky` + `accent-blue` which aren't in tailwind.config.ts — verify)
   - Centralize spacing rhythm so new sections don't accidentally drift

5. **Real sponsor CMS / access-controlled deal room** — *(Risk/Ops)*
   - Replace the un-gated `/sponsors-only` page with authenticated sponsor materials
   - Stub auth check before showing pricing/tiers
   - Per-sponsor view: their materials, their builders, their feedback
   - Foundation for productizing BuilderShip as a tool other event hosts can use

## Additional v2.0-class items that came up but aren't on PUNCHLIST yet

- **Multi-event support**: `/events/[slug]` already works but `data.ts` and seed are
  BuilderShip-shaped. Generalize so the platform can host the next 3 events without
  copy-paste-edit
- **Judge portal**: actual UI for sponsor/AI judges to review submissions, not just
  the rubric on the homepage
- **Leaderboard reveal mechanism**: `scoringConfigJson.public_leaderboard_at`
  exists in seed but no UI consumes it yet
- **PRD reconciliation**: at this point, decide whether to formally rewrite the PRD
  to match shipped scope, or keep BuilderShip as a small subset and document the
  larger platform vision separately

## Suggested sequencing

1. Brand-asset pipeline first (cheap, removes recurring bug class)
2. Idempotent data pipeline (unblocks safer DB evolution)
3. Dynamic per-event OG (foundation for multi-event)
4. Multi-event support (the actual product evolution)
5. Sponsor CMS (productization)
6. Judge portal + leaderboard (operations productization)

## What's explicitly out of scope

- Rebuilding the PRD's "full platform vision" (cloud IDE, workshops player,
  pricing tiers, builder/event-manager apps). If we go there, it's a v3.0
  conversation with founder buy-in, not a v2.0 evolution.
