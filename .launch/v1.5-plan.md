# v1.5 — post-launch reactive (week 1)

> **Worktree:** `.worktrees/v1.5-reactive` (branch `v1.5-reactive` off `main` at `6a729b9`)
> **Window:** First 7 days post-launch (tomorrow → +7d)
> **Trigger:** Tagged after launch lands. Pick items as user feedback comes in.

## Confirmed items from PUNCHLIST.md council synthesis

1. **Instrument the funnel** — *(Product, Marketing)*
   - Add UTM tags + analytics to every share/RSVP CTA
   - Track: homepage hits → CTA clicks → Luma landing → RSVP confirmation
   - Pick: PostHog (free tier, env var `NEXT_PUBLIC_POSTHOG_KEY` already in schema)
     OR Plausible OR a simple `/api/track` endpoint writing to Postgres
   - Today there is zero visibility into where prospects drop off

2. **On-site intent capture** — *(Product)*
   - Email/waitlist form on the homepage BEFORE the Luma handoff
   - We own the lead, can re-engage post-event, measure drop-off at the boundary
   - Minimum: name + email + "what are you building" → Resend signup
   - Schema already has `users` + `eventRegistrations` tables

3. **Structured error monitoring** — *(Engineering)*
   - Add Sentry (env var `SENTRY_DSN` already in schema)
   - Right now a runtime 500 is invisible until a user reports it
   - Wire `instrumentation.ts` per Next 14 conventions

4. **Deploy preview smoke test + Vercel rollback runbook** — *(Engineering)*
   - A 1-page `RUNBOOK.md` for on-call:
     - How to roll back a Vercel deployment (one command via `vercel` CLI or dashboard)
     - How to check Vercel deploy logs
     - How to flush the OG image cache after a copy edit
   - Optional: smoke test in CI that hits the Vercel preview URL and asserts homepage 200 + key strings

5. **"Wall of ships" social-proof surface** — *(Marketing)*
   - Embed accepted applicants' shared X/LinkedIn posts inline on the homepage
   - Makes the apply-by-posting loop self-reinforcing — others see what got picked
   - Manual curation for week 1; could automate via X API later

6. **Weather/cancellation contingency surface** — *(Risk/Ops)*
   - Boat event has no rain-date or refund/cancellation policy on-site
   - Publish: "Boat day weather policy" + a "Event status" banner mechanism
   - Where the banner reads from: feature flag, env var, or `events.statusJson`
   - At minimum: a static FAQ entry + a contact email for cancellation

7. **Capacity/waitlist handling** — *(Risk/Ops)*
   - Define behavior when Luma hits 30 RSVPs
   - On-site: "Waitlist now" CTA instead of "Register"
   - Dock manifest vs. headcount sanity check before boat day

## Items NOT in this scope (defer to v2.0)

- Brand-asset pipeline normalization (structural)
- Real sponsor CMS / authenticated deal room
- Idempotent migration-based data pipeline
