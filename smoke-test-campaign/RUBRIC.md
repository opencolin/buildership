# Smoke-test rubric (locked by the PM council)

## Classification rules

SIX mutually-exclusive verdicts. Evaluate STRICTLY TOP-DOWN — the first rule that matches wins, so clone-fail and empty are decided before any repo code is fetched or run. Exactly ONE verdict per repo. A verdict answers only "can this run as-is?" — NEVER code quality, correctness, or tests. Record stack + entrypoint + first-error for every verdict so the v2 triage agent can act without re-running.

1. clone-fail — `git clone --depth 1 https://github.com/BuilderShip/<name>` does not produce a working tree (404 / private / auth-required / network / LFS-pointer-only / timeout). TERMINAL: no further step runs; everything below assumes a clone exists.

2. empty — clones, but no runnable source: only README/LICENSE/.gitignore/.github/assets, OR a bare scaffold with zero app code (no dependency manifest carrying real deps AND no source files in any supported language; rule of thumb <2 non-doc/non-config source files). "Scaffold with nothing in it."

3. no-entrypoint — real source + a manifest exist, but nothing is startable: a library/SDK, notebook-only, docs site, snippet dump, or a scaffold whose start/entry is absent or a pure stub (e.g. package.json with no dev/start/serve and no bin/server/CLI; Python with no main.py/app.py/manage.py/console_script and no ASGI/WSGI target; Go with no `package main`+`func main`). DISTINGUISHER vs build-fail: we never reached a build to fail because there is no thing to build or launch.

4. build-fail — a clear entrypoint exists and was attempted, but dependency install OR compile OR build/typecheck-as-build errored within the timeout (dep resolution, compile, bundler, typecheck, missing build-time file, OR a step that hit its hard timeout — record "timeout@<step>"). Capture the FIRST error line + the failing command. This is the "tried to run, broke" bucket. A missing-SECRET error does NOT belong here (that is needs-secrets); only genuine dep/compile/type/bundler/timeout failures.

5. needs-secrets — installs and builds/compiles cleanly AND has a clear entrypoint, but cannot actually start/serve without operator-supplied config it does not ship: a committed `.env.example`/`.env.local.example`/`.env.sample`, README/code references to REQUIRED API keys / DATABASE_URL / OAuth / Redis-queue creds, or a startup env-guard that exits non-zero — with no safe committed default. Build is green; only runtime configuration is missing. "Would run the moment you hand it secrets." This is the EXPECTED default for these hackathon repos.

6. runs-clean — installs and (if a build step exists) builds with no error, has an unambiguous entrypoint, AND needs no secret to boot: either no required env, or every required env has a safe committed default. The ONLY verdict implying "git clone -> install -> build" is green with nothing but optional config between it and launch.

TIE-BREAKERS (precedence resolves every overlap):
- build-fail > needs-secrets — if the build never went green, report build-fail even if secrets are also missing (fix the build first). A build error CAUSED by a missing key is still build-fail.
- needs-secrets > runs-clean — ANY unmet required secret demotes to needs-secrets.
- no-entrypoint > build-fail and > runs-clean/needs-secrets — if you cannot identify any entrypoint, it is no-entrypoint even if deps also fail; never report a build break (or a clean run) for something never meant to launch.
- empty / clone-fail are checked first and short-circuit everything.
- POLYGLOT / MONOREPO: classify on the PRIMARY runnable app — the deepest/most-referenced manifest the README or root manifest points at. Note secondary stacks/packages in the issue body; do NOT let them flip the verdict.

## Pass criteria

PASS = verdict in {runs-clean, needs-secrets} — the project is fundamentally sound and the only thing between it and running is configuration. FAIL = {build-fail, no-entrypoint, empty, clone-fail}. needs-secrets is a PASS-WITH-ASTERISK (build green, config missing). We assert "this could run," NOT correctness, NOT a passing test suite, NOT a reachable HTTP 200.

THE PASS GATE (universal): the install/compile step returned exit 0 AND a real entrypoint was named AND the only thing left is secrets-or-nothing. The PASS must come from SHIPPED code + SHIPPED defaults — if making it "run" required writing a secret, hand-crafting a config, or patching a file, downgrade to needs-secrets (config) or build-fail (code). Build-green is the bar; a full live boot is NOT required (most repos cannot boot without secrets).

OPTIONAL START-PROBE (booster, never a downgrade): after a green build you MAY run a short start probe — server binds a port / CLI prints --help / static index serves. A clean probe is bonus evidence noted in the issue. A non-clean probe NEVER turns a green build into build-fail; if the process exits because a key/DB is missing, that is needs-secrets, full stop. Only a genuine dep/compile/bundler error (not a missing-secret exit) is build-fail.

SANDBOX CONTRACT (every step, every repo): run in an isolated `/tmp/st/<name>` clone dir (these give the same parallel isolation worktrees give for our own repo; git worktrees do not apply to external forks). Hard per-step wall-clock timeouts: install <=180s, build <=300s, optional start-probe <=20s — a timeout records build-fail "timeout@<step>", never a hang. First npm pass uses `--ignore-scripts` to blunt postinstall risk (a lifecycle-script-only failure is NOT build-fail — note it and continue). NO Docker image builds. No network egress beyond package registries. No real org credentials / DATABASE_URL ever mounted into a target. Run non-privileged; no servers held open beyond the boot probe.

PER-STACK BAR:
- NODE (package.json): `npm ci` (fallback `npm install`) with `--ignore-scripts` exits 0; if a `build` script exists, `npm run build` exits 0 (Next.js typecheck-on-build counts; non-zero = build-fail). Entrypoint = a dev/start/serve script OR a Next/Vite/Express/bin/CLI target. Lockfile present -> prefer `npm ci`; a lockfile mismatch that only `npm ci` rejects -> retry `npm install` BEFORE calling build-fail. pnpm/yarn lock -> use that PM. PASS-clean only if it would `start` with no required env; else PASS as needs-secrets. No build script (plain Vite dev / CRA) -> install green + a dev entrypoint is enough.
- PYTHON (pyproject.toml / requirements.txt): create a venv; `pip install -e .` or `pip install -r requirements.txt` exits 0 (prefer `uv sync`/Poetry per the committed lockfile). Python has no compile gate, so the build proxy is "imports its own entry module without ModuleNotFoundError": a quick `python -c "import <entry>"` (or `python -m <entry> --help`) is the smoke. Entrypoint = main.py/app.py/manage.py, a uvicorn/gunicorn/FastAPI/Flask/Streamlit target, or a console_script. Install-resolution / missing-build-backend error = build-fail. Import-only library with no entry = no-entrypoint. Required key/DB at import or boot = needs-secrets.
- GO (go.mod): `go build ./...` exits 0 (this is BOTH build and entrypoint proof when a `package main`+`func main` exists, including a documented `cmd/` binary). PASS = build green + at least one main. Compile/dep error = build-fail; library-only (no main) = no-entrypoint. `go vet`/tests not required (run vet opportunistically only).
- RUST (Cargo.toml): `cargo build` exits 0 + a `[[bin]]`/`main.rs` entrypoint = runs-clean (else needs-secrets if a required key blocks boot). Compile/dep error = build-fail; lib-only crate = no-entrypoint. (Few expected.)
- STATIC (index.html, no/inert build manifest): INSPECT ONLY — never run a server, never build images. PASS-clean if a self-contained `index.html` exists at root or the documented dir and its references resolve locally with no required backend. needs-secrets if it hardcodes/expects an API key or backend URL. Missing assets/broken local references with no servable page -> no-entrypoint; no real page -> empty. A static site effectively cannot build-fail. If it actually declares a build (Vite/Astro/Eleventy), evaluate it as NODE above.
- DOCKER-ONLY (Dockerfile, no native manifest): INSPECT ONLY — do NOT build the image (v1 explicitly does not validate image builds). If the Dockerfile has a valid base + a declared CMD/ENTRYPOINT, the entrypoint is proven by intent: record needs-secrets if it expects env, else no-entrypoint. NEVER runs-clean (we did not execute it).

CAPTURE FOR EVERY REPO: detected stack, exact run command found, install ms + build ms, exit code, first-error line (if any), entrypoint path, and the required-secret list.

## Release roadmap (v0.1 → v2.0)

Release phases map onto the existing `smoke-test-campaign/PLAN.md` status board so the next agent resumes cleanly. CADENCE: drive off workflow-completion notifications — `ScheduleWakeup` clamps to ~60s, so true 30s ticks are impossible; use one LONG fallback wakeup as a hang guard, NOT a poll. Each phase is shippable, idempotent (re-running SKIPS any repo whose `🔬 Smoke test` issue already exists), and runs in its own worktree/isolated-clone batch (the .worktrees/ per-release model already in use). Advance only when the prior phase's exit-criterion is met.

v0.1 — Inventory & access [DONE]. 27 forks in `targets.tsv` (14 finalists first, 13 others); clone verified (~3s); org admin confirmed; issues default OFF (has_issues=false) but perms.admin=true so each agent can enable them per-repo. Exit: every target has a name + stack guess + a reachable clone URL or a clone-fail mark.

v0.2 — Rubric & safety baseline [THIS DELIVERABLE — SHIPPING NOW]. The PM council + chair ratify: the 6-verdict taxonomy (precedence + tie-breakers), the per-stack pass bar, the fixed issue template (Verdict / Stack / Run command / Install+Build timing / Required secrets / First error / Repro), AND the sandbox+safety contract (isolated /tmp/st/<name>, `--ignore-scripts`, hard timeouts, NO image builds, no egress beyond registries, no creds mounted, non-privileged). Exit: this doc is FROZEN as the scoring contract — no verdict is ambiguous on a real repo; a 3-repo dry run (1 Node, 1 Python, 1 edge) agrees with manual triage before fan-out.

v0.5 — Fan-out smoke run [RUNNING]. One idempotent agent per repo, isolated /tmp/st/<name>, pipeline clone -> detect -> install -> build -> (optional start-probe) -> classify with the timeouts/safety above. Finalists first. Agents skip any repo whose `🔬 Smoke test` issue already exists. Exit: all 27 carry a verdict + captured evidence (stack, command, install/build ms, first-error, entrypoint, secrets). GATE to v0.7: 27/27 classified.

v0.7 — Safety review gate [NEW — HARD GATE before any GitHub write]. A risk pass scans captured logs for footguns: postinstall that tried to phone home, requested creds, crypto/wallet code, `rm -rf` / `curl|sh` patterns, or secrets accidentally committed in the fork. QUARANTINE anything that tripped the sandbox; do NOT auto-open issues on those until a human eyeballs them. Exit: clean repos greenlit for write; flagged repos parked with a note + reason.

v1.0 — One GitHub issue per repo [PENDING]. For each greenlit (non-quarantined) repo, the agent enables issues on the fork and opens/UPDATES a single `🔬 Smoke test` issue using the fixed template, with the verdict as a label (runs-clean/needs-secrets/build-fail/no-entrypoint/empty/clone-fail). Idempotent on issue title (re-runs edit in place, no dupes). Exit: every non-quarantined fork has its issue; links collected.

v1.5 — Aggregate RESULTS.md [PENDING]. Master table in `smoke-test-campaign/RESULTS.md`: repo | finalist? | stack | verdict | entrypoint | first-error | secrets | issue link — plus a verdict-count rollup and a pass-rate ((runs-clean + needs-secrets) / 27), broken out finalist vs non-finalist, and a "cheap fix?" column. Exit: a single page an organizer can skim; the campaign is fully resumable from this file alone even if v2 never runs.

v2.0 — Triage & fix PRs [NOT STARTED]. For build-fail repos with cheap, high-confidence, SAFE fixes only (lockfile regen, add/pin a missing dep, pin Node/Python, correct an obviously wrong build/start script, fix an obvious typo/import, add a missing `.env.example`): open a branch + PR against the fork from a worktree, re-smoke the branch to confirm it flips to runs-clean/needs-secrets, and link the PR back into the issue + RESULTS.md (flip the label on merge). needs-secrets repos get a DOCUMENTATION PR (how to key it), not code. HARD GUARDRAILS: no feature work, no deep rewrites, no secret provisioning, no Docker, never commit a real secret, never run untrusted build/network/postinstall side effects outside the sandbox, one PR per repo, human-review before merge. OUT OF SCOPE: the ~10 repos that 404'd at fork time (no repo to test). Exit: every cheaply-fixable build-fail has a PR; the rest are documented as won't-fix-now with the blocking reason.

NEVER-DO (every phase): build or run Docker images; mount real org credentials or DATABASE_URL into a target; disable `--ignore-scripts` to "make it work"; give a target network access beyond package registries; run as root; or auto-act on a repo that tripped the v0.7 safety gate. When in doubt, downgrade the verdict and leave a note rather than executing more untrusted code.
